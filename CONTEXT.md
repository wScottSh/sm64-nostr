# CONTEXT — domain glossary

Ubiquitous language for the **airgapped Nostr QR leaderboard** work (ticket [#4](https://github.com/wScottSh/sm64-nostr/issues/4)). Names the good seams so specs, code, and reviews all say the same thing. Architecture vocabulary (module, interface, depth, seam, adapter, leverage, locality) comes from the `/codebase-design` skill and is used here verbatim.

## Pipeline & code shape

- **The pipeline** — the one **deep module** of the feature: `(StarCapture, key) → bytes` (packed payload + QR bitmap). Pure — touches no `MarioState`, no globals, no N64 headers/timers — so it builds and runs off-device. Its **interface is the test surface**.

- **StarCapture** — the plain-old-data struct that *is* the pipeline's input seam: `{course, act, coins, frames, nonce16, keyId}`. The game **glue** fills it at the grab site (`interact_star_or_key`, `interaction.c:812`) from scattered N64 state (course/act globals, `m->numCoins`, `starIndex`) and hashes the content **nonce** in the glue. Nothing N64-specific crosses into the pipeline except this struct.

- **Glue** — the thin game-side code either side of the pipeline seam: the grab-site capture (fills `StarCapture`) and the renderer (consumes the QR bitmap). Deliberately shallow; carries no crypto or format logic.

- **Event profile** — the build-time constants that pin a build to one signing identity + event shape: baked serialization prefix (#13), kind `8064`, `t` tags, `created_at` (#12), pubkey. Emitted as generated `event_profile.h` (recipe mirrors `text_strings.h.in` → `$(BUILD_DIR)/include`).

- **Format descriptor** — the single machine-readable source of truth for the **packed payload** (~113–143 B in **format v3** — a 113 B fixed spine plus the length-prefixed `t`-tag (≤10 B) and signed event name (≤20 B, raised from ≤15 B by spec #91 sub-issue #126); was ~112–122 B in v2, 75 B in v1, #14), emitted by the same generator as the event profile. The ROM **pack adapter** and the host **unpack adapter** both derive from it, so the two sides can't drift. The packed payload is the system's narrowest, most permanent interface — the only artifact crossing ROM → reader → leaderboard.

- **Self-contained event** — the invariant that the QR carries a *complete, already-signed, broadcast-ready* Nostr event: every value in the signed serialization (`pubkey`, `created_at`, `kind`, `tags`, `content`) is fixed on-cartridge before the QR is drawn and is recoverable from the QR alone. No game↔reader out-of-band coordination exists. In **format v2** this forced `pubkey` + `created_at` + the per-game `t` tag onto the wire (v1 wrongly baked them out-of-band). See ADR-0001/0002/0005.

- **Reader** — the strictly **read-only airgap jumper**: a **generic phone camera** scans the **plaintext-URL QR**, opens the URL, and the **website** behind it decodes the payload into the signed event and broadcasts it to a relay — injecting no value and performing no verification. Verification (if any) is the relay's / leaderboard's job. There is **no dedicated companion app**: ADR-0001's dedicated-app premise was an AI assumption the owner never made and is **retracted** (see ADR-0005, the *zero far-side reconstruction* invariant). Since spec #115, sub-issue #119, the reader's source lives in-repo at `reader/`: a static page (`index.html`) that re-grabs the camera (`getUserMedia`) for the N>1 case, reassembles the indexed **fragment** set (below), decodes it via `reader.js` — a JS port of the pipeline's own unpack/serialize/id logic, deriving its wire-format constants from `reader/generated/transport_contract.js` (generated by `tools/gen_transport_contract_js.py` from the SAME `transport_contract.h`/`event_id.h`/`format_descriptor.json` the C pipeline uses, never a hand-copied literal) — recomputes only `id`, and broadcasts to a configured relay.

- **Transport contract (JS)** — `reader/generated/transport_contract.js`, the reader page's own port of the fragment/base32/URL/format-descriptor contract, generated (not hand-transcribed) by `tools/gen_transport_contract_js.py`. Gitignored like every other generated header in this repo (`format_descriptor.h`/`event_profile.h`); regenerated by `npm run generate` / `npm test`'s own pretest step under `reader/`.

- **Internal ports** — sha256 (#6), secp256k1 (#5/#23), qrcodegen (#15). They sit *behind* the pipeline interface as **internal seams** (swappable, each with its own known-answer test), never called by glue. Their C99 requirement stays contained here.

- **QR bitmap** — the pipeline's **output seam**: a 1-bpp bitmap, not framebuffer pixels. The renderer glue blits it via direct RGBA16 writes to the uncached framebuffer (`crash_screen_draw_glyph` precedent, `crash_screen.c:81-101`). Host tests decode the bitmap; encoding is never fused into the framebuffer write. Since ADR-0006's multi-frame transport (spec #115, sub-issue #116), `build_event()`'s output is a **frame set** — a `frame_count` plus that many QR bitmaps (`BuiltEvent::qr_bitmaps[N]`), one per URL-wrapped **fragment** (below) — replacing the earlier single `qr_bitmap` field; N=1 (a single static frame) is the common case, N>1 only when the honest payload overflows one frame's alphanumeric budget once URL-wrapped.

- **Fragment** — ADR-0006's transport envelope unit (spec #115, sub-issue #116; realigned to #101's ratified URL schema by spec #122, sub-issue #123): the packed payload, base32-encoded (`base32.h`, RFC 4648 §6, uppercase `A-Z2-7`, no padding) and split into indexed chunks (`fragment.h`), each prefixed with a fixed-width, `/`-delimited header (its own 0-based index + the total frame count, both base36) and wrapped into the complete per-frame URL `<BASE>#<SEQ>/<TOTAL>/<PAYLOAD>` (`url.h`) — the base URL emitted **verbatim** (never uppercased) and joined to the fragment with a literal `#`. Because the verbatim base can contain bytes outside the QR alphanumeric charset, each frame QR-encodes as **two segments** (`qr_adapter.h`'s `pipeline_qr_encode_two_segment`): a BYTE segment for `<BASE>#` and an ALPHANUMERIC segment for the `/`-delimited fragment tail. Fragments carry their own index, so they reassemble in any order, from any host (the reader's fragment-parse/reassembly interfaces take no base-URL argument and perform no host comparison); the packed payload bytes themselves are unchanged — this is a reversible envelope, not a new wire format.

- **Star-capture overlay** — what the renderer glue actually composites (issue #84, ADR-0004): the QR flush-left at 2px/module and an **authentic SM64 dialog box** to its right (real ia4 glyphs + `gDialogCharWidths`, ROM box-height formula, translucent black), the pair centered inside the 8px overscan band. The pure core (`qr_render.c`) owns all placement/wrap/blend math and is host-tested; the one thing that varies — the dialog font — is an injected **font seam** (`QrRenderFont`), supplied on device from `main_font_lut`/`gDialogCharWidths` and faked in the host test. `QR_RENDER_MODULE_SCALE_PX` (2) is a to-be-photo-tested LED-first bet; fall back to 3/4px there alone. Since ADR-0006's multi-frame transport (sub-issue #118), the N64 shell (`qr_display_n64.c`) cycles through all of `BuiltEvent`'s N frames on this same overlay at a fixed cadence, selected by a pure `(frameCount, tick) -> frameIndex` core (`qr_cycle.h`, one tunable cadence constant, `QR_CYCLE_HOLD_TICKS`); N=1 stays a single static frame, unchanged from before. Because the overlay is a CPU framebuffer blit it cannot write the framebuffer's RDP-only hidden coverage bits, so the anti-aliased VI mode would otherwise bleed 3D silhouette edges through it (issue #89); the shell therefore drops the VI to point-sampled mode (`OS_VI_*_LPN1`) for the overlay's lifetime and restores the anti-aliased mode on dismiss — see ADR-0008.

- **qr_display glue** *(deferred)* — the small shared state machine (`qr_present(bitmap)` / `qr_update(input)→done`) owning time-stop, debounced-A, and the one-shot `memset`, so the "never re-summonable" invariant lives in one place across both save flows.

## Build & provisioning

- **Build wizard** — the single-command build pipeline. A thin host launcher (`build.ps1`/`build.sh`) `docker run -it`s an interactive `/wizard`-style bash orchestrator *inside* the container, which provisions the signing key, runs the one blessed `make` shape, and streams the build. Docker-only; the operator fires one command and a signed ROM comes out. See ADR-0003.

- **Ephemeral per-event key** — the paradigm that a ROM's signing key is the identity of *one game at one event*, minted fresh per build by default, freely overwritten, and never a long-lived identity. Its only recoverable surface is the end-of-run panel (`npub`/`nsec`). Distinct from **origin-provenance** (which the key still provides *within* an event): the key is disposable, the provenance guarantee is not.

- **Event name** *(implemented, spec #75 sub-issue #76)* — a REQUIRED human-readable identity for an event, distinct from `PIPELINE_KEY_LABEL` (registry label) and the per-game `t` tag: an event ROM cannot be built without one. Supplied via the Makefile's `PIPELINE_EVENT_NAME` (no default; `$(error)`s at parse time if unset/empty, mirroring the privkey fail-closed check) and the build wizard's `-EventName` (prompts interactively when omitted). Validated and normalized by `gen_event_profile.py` — uppercase-folded, restricted to `A-Z 0-9 space`, capped at 20 chars (rejected, never truncated, if over; raised from 15 by spec #91 sub-issue #126) — and baked into `include/event_profile.h.in` as `PIPELINE_EVENT_NAME`/`PIPELINE_EVENT_NAME_LEN`. As of format v3 (spec #109, sub-issue #111) this value is no longer display-only: `build_event()`'s pack stage also sources it, so it rides both the castle HUD corner AND the QR wire (`NAME_LEN`/`NAME`) AND the signed NIP-01 `["n",...]` tag — see the Format descriptor entry above.

## Timing & flow

- **Capture@grab / display@park** — values are frozen at the moment of the star grab (nonce included); the QR is shown later when Mario parks. See #17.

## Trust & provenance

- **Origin-provenance** — the guarantee the signature actually provides: "produced by the private per-event ROM the operator built for event X", *not* honest play. The unextractable-key problem is **dissolved by distribution control** (private binary, never distributed), per #9/#10.

## Sandbox seams

The fork deliberately opens progression gates so a fresh file plays as an open sandbox. Each such gate is a **sandbox seam**: a single, named, always-open decision point, kept together so the sandbox behavior is discoverable in one place.

- **Sandbox seam A** — fixed mask of "unlocked" progress flags (`SAVE_FLAG_SANDBOX_UNLOCK_MASK`) OR'd into `save_file_get_flags()` at read-time so a fresh save behaves as an open sandbox. Excludes star-collection flags; with sandbox seam F now gating star-collection recording off entirely, the star bitfield is never written in the first place, so HUD star count stays 0 and course progress stays honest by construction, not merely by this mask's exclusion.

- **Sandbox seam B** — `save_file_star_gate_is_open()`, an always-open star-requirement predicate substituted at the live star-count comparison sites (star-count doors, endless-staircase warp, MIPS, Toad checks, the outside-castle cannon grill `bhvHiddenAt120Stars` at 120 stars, and the look-up warp to Wing Mario Over the Rainbow at 10 stars) so every star gate is passable at 0 stars. Reward/cosmetic star-count milestones that don't block access — Yoshi spawning on the roof at 120, the fat racing-penguin variant at 120, and the pre-70-star castle-staircase music cue — are deliberately left on their raw comparisons and unchanged.

- **Star-select act gate (sandbox seam C)** — a menu-selection-only gate: all six of a course's act stars are always visible and selectable in the star-select menu, regardless of collection progress. Each slot's rendered model still follows the real per-course star flags; with sandbox seam F gating star-collection recording off, those flags are now never set, so every slot renders translucent (uncollected) and stars are infinitely re-grabbable. Does not touch `sObtainedStars`, the star bitfield, level object spawning, or the 100-coin star path — selectability only.

- **Sandbox seam D — intro suppression** — `save_file_intro_is_suppressed()`, an always-TRUE predicate substituted at two decision points so it stays one gate, not two:
  - The spawn-time action-select decision point in `init_level` (`level_update.c`) so a pristine file selects `ACT_IDLE` instead of `ACT_INTRO_CUTSCENE`. Since the opening cutscene's `CAM_EVENT_START_INTRO` is never set, `CUTSCENE_INTRO_PEACH` never runs and DIALOG_033 (the pipe-exit text) is removed transitively, with no separate edit. The intro-only white fade-in transition is skipped along with it, so the normal star-warp transition plays.
  - The `gNeverEnteredCastle` assignment in `lvl_init_from_save_file` (`level_update.c`), which is forced `FALSE` ("already entered") whenever the predicate is suppressed. `bhvCameraLakitu` (the intro Lakitu that blocks the bridge for DIALOG_034) and `act_warp_door_spawn`'s Bowser taunt branch (DIALOG_021) both gate on this same flag, so both are removed at once. As a side effect, `set_background_music` (`sound_init.c`) no longer skips the castle-entry music cue, so normal castle music plays immediately instead of the vanilla quiet first-entry cue. A third vanilla reader, the `gNeverEnteredCastle` self-clear-and-start-music hook in `act_reading_automatic_dialog` (`mario_actions_cutscene.c`, fires after the first star dialog), is now dead code on a pristine file: the flag is already `FALSE` by the time it would run, so the hook's own `play_cutscene_music` call never fires. Harmless — the music it would start is already playing — but `lvl_init_from_save_file` becomes the sole effective writer while this seam is active.

  Force-off, not delete: vanilla `act_intro_cutscene`, `bhvCameraLakitu`'s intro branch, and the Bowser taunt branch all stay in the tree, unreached.

- **Sandbox seam E — cannon suppression** — `save_file_cannons_are_forced_open()`, an always-TRUE predicate consulted at the top of the existing `save_file_is_cannon_unlocked()` accessor, before its real per-course cannon-bit read. Keeping the decision inside the single existing accessor (rather than adding a second gate) means both cannon-lid decision points (`bhv_cannon_closed_init`/`bhv_cannon_closed_loop`, `cannon_door.inc.c`) and the Bob-omb Buddy cannon dialog (`bobomb_buddy_cannon_dialog`, `bobomb.inc.c`) see a consistently-open cannon: the Buddy checks the same accessor at `BOBOMB_BUDDY_CANNON_UNOPENED` and skips straight to `BOBOMB_BUDDY_CANNON_OPENED` instead of offering to unlock. Force-off, not delete: the vanilla per-course bit read stays in the tree but is unreached.

- **Sandbox seam F — star-collection suppression** — `save_file_star_collection_is_recorded()`, an always-FALSE predicate guarding the single star-grab record call in `interact_star_or_key` (`interaction.c:970`) so `save_file_collect_star_or_key()` — and the star bitfield write inside it — is skipped on every star grab. The QR build/capture (`interaction.c:~900-967`) runs upstream of this guard and is untouched; the star's content is still captured and encoded exactly as before, only the save-file record of "this star was collected" never happens. No separate dialog-suppression predicate is needed: with the bitfield never written, `save_file_get_total_star_count()` never rises above 0, so the milestone-dialog chooser never crosses a threshold and the Power Star / milestone dialog series is suppressed transitively. Confirmed by `docs/research/star-persistence-collectability.md`: no star becomes un-grabbable when its record is skipped (hitboxes are set unconditionally; the 100-coin star keys off the live per-attempt coin count, not any saved flag) — so every star, including the 100-coin star, stays infinitely re-grabbable, the HUD star count stays pinned at 0, and every star-select slot renders translucent (seam C). Force-off, not delete: the vanilla record call stays in the tree but is unreached while this predicate returns FALSE, matching seams D/E.
